# backend

The Go backend for Issho: a modular monolith serving a ConnectRPC API. It uses Postgres (Supabase) through pgx and sqlc, and goose for migrations. Architecture notes are in [../docs/architecture.md](../docs/architecture.md).

## Layout

| Path | Contents |
|---|---|
| `cmd/api/` | API server: wires config, DB pool, the JWKS verifier and handlers, then serves HTTP/1.1 and h2c on `API_ADDR` |
| `cmd/worker/` | Background jobs on River (`internal/worker`): starts the River client and stops it gracefully on SIGINT/SIGTERM |
| `cmd/tool/` | Ops CLI: `migrate <goose command>`, `seed [-catalog file] [-venue-categories file] <citypack.json>...` (also applies catalogue merges: `replaces`), `build-matrix [-dry-run] <city>`, `discover-venues [-dry-run] [-categories ids] [-max-requests n] <city>`, `area-boundaries [-threshold deg] <citypack.json>` (areas' outlines from OpenStreetMap by `osm_id`; no database; `make boundaries CITY=…`), `email-templates [-source file] [-out dir] [-config file]` (sign-in emails in every language of `supabase/templates/source.json`, machine-translated; needs `GOOGLE_TRANSLATE_API_KEY`), `simulate [-users n] [-seed n] [-month n] [-config json] [-seeds n] [-thin x] [-variety x] [-neutral x] <citypack.json>...` (no database needed; `-seeds` averages that many cities, the other three set how simulated people respond to a plan's shape), `set-admin [-revoke] <email>` (the admin SPA's role, below), `set-translator <email> <ja,es,...>` / `set-translator -revoke <email>` (the translation editor only, for those languages), `ui-strings <apps/mobile/src/i18n>` (checks and stamps the UI text's human versions and checks the notes; run by `make gen`), `translate-compare [-langs ja,es,pl,zh] [-out file.json]` (Google and Gemini on every UI string, side by side, for review; stores nothing; needs both keys), `ui-bundle -api <url>` (`make ui-bundle`: the city packs' languages as that API serves them, bundled into the app; no database) |
| `internal/platform/config` | Environment variables → `Config` |
| `internal/platform/db` | pgx pool and goose migration runner |
| `internal/platform/auth` | Supabase JWT verification (JWKS) and the Connect auth interceptor; `Require` and `RequireAdmin` for handlers |
| `internal/platform/pgconv` | `Deref` (nullable text to string), `Nullable` (zero uuid to NULL) and `Time` (non-NULL timestamptz): the one copy of the conversions the sqlc types need |
| `internal/platform/validate` | Runs the `buf.validate` rules from `proto/` on every request (last interceptor, after auth); a violation is `errs.Invalid` |
| `internal/platform/i18n` | Language rules: what to display from text resolved into the primary and secondary languages (`Pair`, called by `translate.Service.ResolvePair`; used directly only for never-translated area names), ISO 639-1 validation |
| `internal/translate` | Text in any language on demand: stored text → `app.translations` cache → `Translator`, with in-flight de-duplication, a bounded wait and background completion; `ResolvePair` for the reader's primary + secondary languages at once, ready to show (the one place the language rule is applied); `Prefill` for content that must exist in given languages (events) |
| `internal/translate/google` | `Translator` using Google Cloud Translation Basic (v2): plain-text mode, batches of ≤ 128 strings and ~5,000 characters |
| `internal/translate/gemini` | `Translator` using Gemini (`gemini-3.8-flash`), the default: each string's context plus the translation guide (`internal/translate/guide.md`: voice, the product's name, terms such as crew, register per language), 40 strings per call, 4 calls side by side. `Draft`, the one call made inside a request (the translation editor's Suggest), has a 60 s total budget (`InteractiveBudget`, retries included) and returns `translate.ErrBudget`, which the handler answers as `Unavailable` with the `TIMED_OUT` reason; `Translate` runs detached from the request and keeps its longer budget. Editing the guide doesn't redo cached translations: delete the unreviewed `app.translations` rows of the languages concerned |
| `internal/translate/translators` | Picks the translator from `TRANSLATOR` for the API, the worker and the tools |
| `internal/platform/httpjson` | The one client policy for outside JSON APIs (Google, GitHub, Expo, Supabase): up to 3 attempts with jittered backoff on resets, timeouts, 429 and 5xx; `Retry-After` up to 30 s and never past the context deadline; POST/PATCH retried only when the caller sets `Idempotent`; one trace span per call from a path template (no query string); a non-2xx answer is an `errs.Upstream` whose cause (`*httpjson.StatusError`) holds the body (cut to 2 KB) for logs and Sentry only. **What it logs:** one `upstream error` warn line per failed call with service, method, route template, status and the body cut to 512 characters, never the URL, query or headers; `HideBody` (Supabase and Expo) drops the body from the line, the error and the cause; statuses a caller expects (a 404 probe, GitHub's 422 conflict, Supabase's 404 on delete) log at debug and leave the span ok. `RetryTimeouts` is off for Gemini (billed calls) and on elsewhere |
| `internal/platform/googleapi` | Key-based Google APIs (Maps, Translation, Gemini) on `httpjson`: key in a header, every call marked idempotent (queries and generation). `MaxRetries` and `Backoff` are the embedded client's |
| `internal/platform/sentry` | Error reporting when `SENTRY_DSN` is set, a no-op otherwise: `Report`, `Handler` (panics), `JobErrors` (River), `StartHTTP` (the outside-call span `httpjson` uses) |
| `internal/platform/errs` | The one error shape: `Invalid`, `NotFound`, `Precondition(reason, …)`, `Denied(reason, …)`/`Forbidden`, `Unauthenticated` and `Upstream(service, err)` build errors; `Interceptor` maps each kind to its Connect code, adds an `ErrorReasonDetail` when there is a reason, reports `Upstream` and `internal` errors to Sentry, and returns a generic `internal error` for anything else (no leaked details). Add a reason to `proto/issho/v1/errors.proto` only when a screen needs it. `*errs.Error` also answers `errors.As(…, *connect.Error)`, so `connect.CodeOf` works in handler tests |
| `internal/platform/paging` | AIP-158 paging for the admin lists: `Size` (page_size 0 = 50, clamped to 200), `Open`/`Encode` for opaque keyset tokens bound to a list and its filters (another list or filter, or garbage, is `InvalidArgument`), `Trim` for the extra row that says there is a next page |
| `internal/platform/supabase` | Supabase admin API client (account deletion, the admin role), using the secret key, on `httpjson` |
| `internal/moderation` | `ModerationService`: the admin SPA's moderation queue (reports, flags, crew leave reasons) and suspensions; admins only. `Service` suspends and lifts: `Suspend` inserts the suspension and the `remove_suspended` job in one transaction (`river.Client.InsertTx`) and tells the API's check only after the commit; `Remover` is what the job runs |
| `internal/platform/deadline` | Unary-RPC deadline interceptor: 30 s by default (never longer than the caller's), per-procedure overrides (`0` = none) from `cmd/api/limits.go`; a handler cut off answers `DeadlineExceeded` |
| `internal/health` | `HealthService`; the database ping is bounded to 2 s, so a hung database reads as `database_ok = false` instead of hanging |
| `internal/identity` | `IdentityService`: app account on top of Supabase users (get, delete) |
| `internal/catalog` | `CatalogService`: activity catalogue with city overrides, cities and areas, language names (CLDR via `golang.org/x/text`) |
| `internal/profile` | `ProfileService`: the caller's own profile (validation in `validate.go`, one-transaction save in `service.go`); `ConductVersion` |
| `internal/tagging` | Free-text interests → suggested activities (`Service.Suggest`: input limits, city catalogue, drops unknown ids, keeps the strongest level per activity) behind the `Tagger` interface |
| `internal/platform/gemini` | Shared Gemini client on Agent Platform: `generateContent` with a system prompt, a user turn and a JSON response schema; returns the answer text, `ErrDeclined` for blocked or safety-stopped answers. Used by tagging and walks |
| `internal/walks` | **Walk composer**: a `Proposer` (the model) proposes a walk from its own knowledge (meeting place, 4–7 stops on the theme, a place to finish), then Places Text Search checks every place (exists under the model's name, compared loosely in memory since Text Search returns its nearest match for anything; open; within 3 km of the area's centre; the right kind for a station, café, bar, temple or shrine; not a duplicate), failing stops are dropped, Routes walks them in the best order (`optimizeWaypointOrder`), an outlier stop more than 20 min away is dropped, and the whole walk must take 2–4 hours with at most 100 min walking. A walk that fails goes back to the model once with the problems named (its own place names and our rules only, never Google content), then is `*Rejected` |
| `internal/walks/claude` | `Proposer` using Claude (Anthropic Go SDK): same prompt and schema as Gemini (`walks.SystemPrompt`, `walks.ProposalSchema`), structured outputs, effort per variant, no tools and no refusal fallback (a benchmark must measure the model it names) |
| `internal/walks/bench` | **Walk benchmark**: 38 cases (`cases.json`: every walking theme, Tokyo and Austin, known, mid, quiet and hard areas, several months and parts of the day) run through the production composer for each variant (`provider:model[:effort]`), with reps; results, errors and traces as JSONL; blind pairwise judging by a jury (one Claude, one Gemini) in both orders on six criteria (theme, flow, social, notes, local, overall) plus doubted claims; a blind human review sheet whose answers calibrate the judges; a Markdown report with 95% intervals. Judges see only model-written text, never Google content or Routes times. `tool walk-bench`, below |
| `internal/walks/gemini` | `Proposer` using `gemini-3.8-flash` (medium thinking, 5 min per attempt) with no grounding: grounded answers may only be shown to the person who asked, not stored. `eval_test.go` composes real walks for review |
| `internal/tagging/gemini` | `Tagger` using Gemini (`gemini-3.5-flash-lite`) on Google Cloud's **Agent Platform** (formerly Vertex AI): `generateContent` over REST with a Google Cloud API key, via `internal/platform/googleapi`. A response schema that only allows the city's activity ids, low thinking, 20 s deadline; blocked or safety-stopped answers count as "no suggestion". `testdata/eval.json` + `eval_test.go` is the multilingual eval set |
| `internal/emailtemplates` | Builds the multilingual Supabase sign-in email templates and subjects from one English source: branches on `.Data.lang`, English fallback, escaping and checks that no translation can break the template or `config.toml` |
| `internal/uistrings` | `UIService`: the app's UI text in any language. `en.json` and `human/` are copies of `apps/mobile/src/i18n/` made by `make gen`; only those strings are translated. Human versions (`human.go`) replace single strings when they were written for today's English; the rest is machine-translated |
| `internal/translations` | `TranslationService`: the admin SPA's translation editor, for admins and translators (their languages only). UI strings are saved as human versions through **one rolling pull request per language** (`translations/<lang>-<time>` branches; each save is one commit with both copies of `human/<lang>.json`, retried once if the branch moved); catalogue text (activity and city names) is corrected in `app.translations` |
| `internal/cities` | City-pack, catalogue and venue-category JSON formats; validation and seeding. `Apply` (the admin SPA's and `tool seed`'s apply: makes the database match a pack, so it also deletes dropped overrides, deletes unreferenced dropped areas, moves a `replaces`d area's people, crews and plans, and refuses with `ErrRefused` when that would lose data; finds new or moved areas with the pure `DiffAreas` and rebuilds the travel times), `DiscoverAreaVenues` (one area's Nearby Searches), `PackStatuses` and `CatalogActivities` (what the Cities page lists) |
| `internal/maps` | Provider-neutral geo interfaces (`Router` for travel-time matrices, `PlaceSearcher` for nearby places) |
| `internal/maps/mapstest` | `Fake`: an in-memory `Router`, `PlaceSearcher` and `PlaceSearch` for tests (canned places and search results, a travel time, injected errors, call counts). Used by the `cities`, `citypacks` and `curation` tests |
| `internal/adminjobs` | The admin SPA's long operations as River jobs: the args (`ApplyCityPackArgs`, unique per city and pack hash; `DiscoverAreaVenuesArgs`, unique per city and area), their queue (`maintenance`), time limits and attempts, the functions the worker runs (`ApplyCityPack`, `DiscoverAreaVenues`: they call `cities` and return what to record), the `Output` a job records (result or failure with a message and an `ErrorReason`; error text from Google or the database never goes in it) and `AdminService`'s handler (`GetAdminJob`: River's state and times plus the recorded output). `NewClient` is the API's insert-only River client |
| `internal/citypacks` | `CityPackService` handler (`handler.go`): checks the admin, maps protos, proposes pull requests on GitHub and calls `cities` for the database side; GitHub's and Google's error text is logged, not sent to the client |
| `internal/curation` | `CurationService`: `Service` (`service.go`: listing, `SetStatus`, `Search`, `Add`, and the pure `fits` and `nearest` rules) and `Handler` (admin check and proto mapping only) |
| `internal/maps/google` | Google implementation: Routes API (Compute Route Matrix), Places API (New) Nearby Search and Place Details (`Details`: localised name, short address, Maps link, location) over REST, with retries on 429/5xx. `placetypes.txt` is a snapshot of valid place types. |
| `internal/matching` | The matching engine (M4), pure: no I/O, deterministic. `Suggest` (plans without a date), `Feed` (plans ranked for one person, with map levels), `Schedule` (date and groups from signups); `Violation` checks a group's hard rules; `ParseConfig` reads a city's overrides. See [Matching](#matching) |
| `internal/matching/sim` | Synthetic users for any city pack (estimated travel times, made-up venues, guessed signup behaviour); runs suggest → signups → schedule and checks the output |
| `internal/worker` | River jobs: `match_all` (periodic, hourly, and once on start) queues a `match_city` pass per city, which runs `plans.Runner.Match` (settle, schedule, suggest, meeting places, routes, in that order, below) and, once that succeeds, queues `crews_city` for the city: the crew pass, retried on its own (up to 5 attempts) so a crews failure never re-runs matching. One pass of each per city is queued or running at a time (unique jobs). River's tables live in the `river` schema |
| `internal/chatws` | Chat rooms over WebSocket (`/ws/chat`): a `Hub` holding one connection per process listening on `chat` and `chat_typing` (reconnecting after errors) that wakes the sockets open on a room and passes on typing notices, and the handler (first-message auth, everything through `chat.Service`: access checked again on every read and typing notice, and a suspended person's next send closes the socket (4403) using the API's in-memory suspended list, catch-up then live messages drained a page at a time, typing notices both ways, pings every 30 s). The API's request contexts end on shutdown, which closes the sockets (`Shutdown` doesn't track hijacked connections) |
| `internal/plans` | `PlanService` (`handler.go`, `service.go`: the caller's feed, a plan, signing up and withdrawing), `Runner` (the worker's passes: `Schedule` checks every open plan, `Suggest` opens plans up to the city's cap) and `LoadCity` (a city's matching input from the database), plus the store. Stores open plans, signups and scheduled events (M6) and converts them to and from `internal/matching`'s types: `Create`, `ListOpen` (with signup counts), `SaveSignup` (times replaced wholesale), `LoadSignups` (adds the occasions people are already invited to, so nobody is double-booked), `SaveEvent` (event, groups and invitations; invited people stop waiting), `NextRound`, `Close`. Saves lock the plan row, so a signup lands either before a round is scheduled or in the next one |
| `internal/notifications` | Push notifications end to end: `Enqueue` (the outbox write, in the caller's transaction), `Notifier.Send` (the worker's send pass through `internal/push`), `CheckReceipts` and dropping dead device tokens. Owns `app.notifications`, `app.push_tickets` and their queries (`db/queries/notifications.sql`). It doesn't write any text: `plans` and `crews` each register a `Renderer` for their kinds at startup (`cmd/worker`), and it imports neither. A `Renderer` returns one `Result` per item: content, *skip* (the plan or crew was deleted: the notification is marked sent, no push) or an error (only that item fails: `attempts` goes up, it is retried until 5, and the rest of the batch is sent). `DeleteOld` (the daily `retention` job) removes notifications older than 30 days that were sent or ran out of attempts. `plans.ClosePlanNoGroup` and `QueueFeedbackRequests` still insert `plan_no_group` / `event_feedback` rows in SQL, to stay atomic with (and idempotent for) the update or scan that causes them |
| `internal/crews` | `CrewService` (`handler.go`, `crews.go`: the caller's crews, answering an offer, leaving with a reason, reporting a member), `Membership` (`membership.go`: every rule about one person's place in a crew, pure, with table tests), `ChatAccess` (`chat.go`: lets members of an active crew into its chat room), `Runner.Pass` (the worker's crew pass, below) and `Service.RemoveFromAll` (suspensions). Uses `internal/plans` for cities and report rules |
| `internal/chat` | Chat rooms for events and crews, one module: a `Room` (kind and id), `Service` (latest and after-a-cursor reads, `Send` with cleaning, limits and `NOTIFY chat`, `Typed`) and `Handler` (`ChatService`). Each owner plugs in an `Access` that says who may read, whether they may write now and the window (`plans.ChatAccess` for event rooms, `crews.ChatAccess` for crew rooms); `chat` imports neither. Posting locks the room's row (`event_groups` or `crews`) so ids commit in order and the id cursor never skips a message; crews' suggested plans (`PostPlan`) take the same lock. Also deletes old event chats (settle) and, in the daily `retention` job, the chats of crews closed or lapsed more than 30 days ago (`DeleteOldCrewChats`) |
| `internal/testfixture` | A throwaway city, area, activity and users for integration tests, removed afterwards; shared so packages that import `plans` can test without an import cycle |
| `internal/geo` | Builds a city's travel-time matrix and venue list through the `maps` interfaces, and stores them. `RebuildMatrix` (load, build, save) is shared by the worker's refresh, `tool build-matrix` and the admin SPA's apply; `ErrCityNotFound` tells an unseeded city from a database failure |
| `db/migrations/` | goose SQL migrations (embedded via `db/embed.go`) |
| `db/queries/` | sqlc queries |
| `gen/` | **Generated.** `gen/issho` (protobuf/Connect), `gen/dbgen` (sqlc). Don't edit; run `make gen`. |

## Configuration

Every process reads its environment through `internal/platform/config` (`Load` for the API, `LoadWorker`, `LoadTool`); `cmd/tool` has no `os.Getenv` of its own.

### `APP_ENV` and what production requires

`APP_ENV` is `development` (the default), `preview` or `production`; anything else is a startup error. Outside production every key below is optional and a missing one only warns. With `APP_ENV=production`, `Load` and `LoadWorker` fail with **one error naming every missing key**, so a deploy with a gap never starts (Kamal's `/up` health check keeps the old container). `tool` requires nothing: each subcommand checks the keys it uses.

| Key | API | Worker | Why production needs it |
|---|---|---|---|
| `DATABASE_URL` (worker: `WORKER_DATABASE_URL` or `DATABASE_URL`) | required | required | Everything |
| `SUPABASE_URL` | required | | Token verification (the JWKS) |
| `SUPABASE_SECRET_KEY` | required | | Account deletion, roles |
| `SENTRY_DSN` | required | required | Errors must not go unseen |
| `GITHUB_TOKEN` | required | required | The editors propose changes by pull request; both processes follow merged UI translations. A refused token (401/403) is a startup error in production, a warning elsewhere. |
| `GOOGLE_MAPS_API_KEY` | required | required | Venue names (API); travel-time rebuilds, opening hours (worker) |
| `GOOGLE_GEMINI_API_KEY` | with `TRANSLATOR=gemini` (the default) | required | Translator; the worker also composes walks with it |
| `GOOGLE_TRANSLATE_API_KEY` | with `TRANSLATOR=google` | with `TRANSLATOR=google` | Translator |
| `EXPO_ACCESS_TOKEN` | | required | Push delivery |

`SENTRY_ENVIRONMENT` defaults to `APP_ENV`. Set `APP_ENV` in each deployment: `config/deploy.production.yml` sets `preview` for the hosted API and worker, which point at `issho-dev`; `production` is for a future real production environment.

## Run

```sh
supabase start                 # from repo root; see ../supabase/README.md
make migrate-up seed api       # from repo root
make worker                    # background jobs (another terminal)
```

Or from this directory: `go run ./cmd/tool migrate up`, `go run ./cmd/tool seed ../data/citypacks/tokyo.json`, `go run ./cmd/api`.

### Container image

`Dockerfile` builds one image with all three binaries (`api` by default, `worker`, `tool`) and `data/` for seeding; Kamal deploys it ([../docs/deploy.md](../docs/deploy.md)). Build it from the repository root:

```sh
docker build -f backend/Dockerfile --build-arg VERSION=$(git rev-parse --short HEAD) -t issho-backend .
DB='postgres://postgres:postgres@host.docker.internal:54322/postgres?sslmode=disable'   # the local stack, from a container
docker run --rm -e DATABASE_URL="$DB" issho-backend tool migrate status
docker run --rm -p 8095:8080 -e DATABASE_URL="$DB" -e SUPABASE_URL=http://host.docker.internal:54321 issho-backend
docker run --rm -e DATABASE_URL="$DB" issho-backend worker
```

The runtime image is distroless (no shell, non-root); `.dockerignore` keeps everything but `backend/` and `data/` (and any env file) out of the build. The Go module and build caches are BuildKit cache mounts, so a rebuild after a code change only recompiles what changed, provided BuildKit's garbage collector keeps them: if every build recompiles from scratch, raise its limit (Docker's `builder.gc` setting; on OrbStack, `~/.orbstack/config/docker.json`). CI builds it on every PR.

## API endpoints

The full reference, generated from the proto comments, is in **[../docs/generated/api.md](../docs/generated/api.md)**. All RPCs are `POST /<package>.<Service>/<Method>` with a JSON body (`Content-Type: application/json`) or binary protobuf.

| Endpoint | Auth | Purpose |
|---|---|---|

**Error hygiene:** handlers and services return `errs` constructors (`Invalid`, `NotFound`, `Precondition`/`Refused`, `Denied`/`Forbidden`, `Unauthenticated`, `Upstream`) for anything the caller should see, never `*connect.Error`; the `errs` interceptor turns each kind into its Connect code (plus a reason detail when there is one). `Upstream` errors keep the outside service's text in the log and Sentry only. ### Authentication
- Clients send `Authorization: Bearer <Supabase access token>`.
- Tokens must:
  - be signed **ES256 or RS256** with a key from the project JWKS (HS256 is rejected)
  - have issuer `$SUPABASE_URL/auth/v1`
  - have audience `authenticated`
  - have an `exp` claim that hasn't passed
- **Limits** (`cmd/api/limits.go`): request bodies over 1 MiB fail with `ResourceExhausted` (the biggest real request, a city pack, is ~15 kB; raise it per handler with a reason if one needs more); unary RPCs get a 30 s deadline, except `ProposeCityPack` (2 min) and `DraftAppString` (90 s: a Gemini call with its own 60 s budget); `ApplyCityPack` and `DiscoverAreaVenues` only queue a job, so they take the default. The `http.Server` has `ReadHeaderTimeout` 10 s, `ReadTimeout` 30 s and `IdleTimeout` 120 s, and **no `WriteTimeout`**, because `/ws/chat` shares it and a write deadline would cut the sockets.
- **Deny-by-default:** every RPC requires auth unless it's listed as public in `cmd/api/main.go` (`HealthService.Check`, `UIService.GetStrings`).
- **Suspended accounts** (`app.suspensions`, set by `ModerationService.SuspendPerson`): `moderation.Gate` refuses every call from them with `permission_denied` / `account suspended`, except `IdentityService.GetMe` (which returns `suspended: true`, so the app shows a suspended screen), `DeleteAccount` and `PushService.UnregisterPushToken` (signing out). The chat socket refuses them too. The check keeps everyone suspended in memory, reloaded every 15 s (at once on the instance that made the change). Suspending also queues `remove_suspended` in the suspension's own transaction (so a suspension never exists without its cleanup being queued, and the reverse), and that job takes them out of their open signups, outings that haven't started (an invitation declined, a confirmed place cancelled, the group re-opening or cancelled as if they'd cancelled themselves) and crews (leaving an active one, which closes if one member is left; declining an offer): `plans.Service.RemoveFromUpcoming` and then `crews.Service.RemoveFromAll`, both safe to repeat; River retries a failed run (10 attempts, 2 min each), the job is unique by person (suspending twice while one is queued adds none) and does nothing if the suspension was lifted before it ran. If it exhausts its attempts, suspending the person again queues a fresh one. Matching (`ListMatchingUsers`), crew offers (`ListCityMetPairs`) and push (`ListPushTokens`) leave them out while it lasts. Lifting doesn't put them back into anything.
- **Admins** are ordinary Supabase users with `app_metadata.admin = true` (only the service role can change `app_metadata`; `user_metadata`, which users can edit, is never read). Grant or remove it with `go run ./cmd/tool set-admin [-revoke] <email>` (needs `DATABASE_URL`, `SUPABASE_URL` and `SUPABASE_SECRET_KEY`; the person must have signed in once). It's carried in the access token, so it takes effect at the next token refresh (at most an hour; signing out and in applies it at once). Admin-only services are listed in `auth.AdminOnly` in `cmd/api/main.go`, so every RPC they have, new ones included, is covered; handlers check again.

## Migrations

```sh
go run ./cmd/tool migrate up        # apply all
go run ./cmd/tool migrate down      # roll back one
go run ./cmd/tool migrate status
```

- The history starts at `db/migrations/00001_baseline.sql` (the pre-production history squashed, #160), then `00002_river.go`. Write new files as `db/migrations/000NN_name.sql` with `-- +goose Up` / `-- +goose Down` sections. Wrap multi-statement blocks (`DO $$ … $$`) in `-- +goose StatementBegin/End`.
- goose records its versions in `goose.db_version`, in a schema of its own. Not `public`, which Supabase's Data API would expose. Not `app`, which the baseline's Down drops.
- **River's tables** (the worker's job queue) are created by `00002_river.go` (`db/river.go`), a Go migration that runs River's own migrator up to `RiverVersion` in the `river` schema; Down drops the schema. When a River upgrade brings a new schema version, add a goose migration that migrates up to it, so goose stays the one owner of migration order.
- Supabase-only statements (the `auth.users` foreign key, revoking `anon`) are guarded with `IF EXISTS` checks, so the same migrations also run on plain Postgres.
- **PostGIS is in the `extensions` schema**, as on hosted Supabase (not `public`: advisor 0014). Migrations write its types schema-qualified (`extensions.geography`), and sqlc's override names `extensions.geography`. Queries use the PostGIS functions unqualified: the `postgres` role's `search_path` includes `extensions` on Supabase (local, hosted and CI's image), so the pool needs no setting of its own. A database without that, such as plain `postgis/postgis`, won't run the queries.

### Domain rules as views

Rules that several queries need live once, as views in `app` (`00003_domain_rule_views.sql`; `security_invoker`, no grants to `anon`/`authenticated`). Queries read the view and never restate the rule; Postgres inlines them, so the plans are the same as hand-written joins.

- `app.attendance`: one row per group membership, with `user_id`, `group_id`, `event_id`, `date`, `response`, `went_ahead` (the outing is `done` and the group wasn't cancelled) and `attended`. **Attended** = confirmed, the group went ahead, and they checked in or their feedback says they went; feedback that says they didn't go wins over a check-in. Matching's reliability and newcomer count (`ListMatchingUsers`), the metrics and **met** pairs (`ListCityMetPairs`: two people who both attended the same group) all use it.
- `app.suspended_users`: `user_id` (and `suspension_id`) of everyone suspended now. Every "not suspended" check is `not exists (select 1 from app.suspended_users …)`. The partial unique index's `on conflict … where lifted_at is null` in `InsertSuspension` is the one place the predicate remains, because Postgres needs it to pick the index.
- `app.kept_apart`: directional pairs (`user_id`, `other_id`) from reports and "rather not" picks, read by `ListCityBlocks` and `ListFriendPicks`. `ListCityCrewAversions` is not one: it is about who declined or left a crew, not a report or a pick, so it stays its own query.

`internal/testfixture/rules_test.go` covers all three.

### Migration policy

- **Production only migrates forward.** A mistake is fixed with a new migration, never with `down`.
- **Down sections exist for local work and CI's up → down → up.** A Down that would delete or rewrite rows first checks whether any exist and raises an exception if so (the baseline's, and River's, refuse when `app.users` has rows).
- **Changing an enum-like check** (`check (x in (...))`): add the new constraint `NOT VALID`, `VALIDATE` it, then drop the old one. Don't drop and re-add in one statement: that rescans the table under a lock and, if it fails, leaves a window without the check.
- **From the M11 cutover on, dropping or renaming a column takes two deploys:** the code stops using it, then a later migration drops it. During a Kamal deploy the old container is still running against the new schema.
- **Migrations that lock busy tables set `lock_timeout`** (`set local lock_timeout = '5s'`), so they fail and roll back rather than queue every other query behind them.

## Seeding

`cmd/tool seed` validates and upserts `../data/venue-categories.json` and `../data/activities.json`, then each city pack given (`make seed` loads them all) through `cities.Apply`, the only way to write a pack. With `GOOGLE_MAPS_API_KEY` set it also builds the travel times of new or moved areas; without it they are skipped (logged). It's idempotent, and a pack is authoritative: overrides and areas it no longer lists are deleted (an area still used by people, crews or plans, or holding curated venues, refuses the apply unless it is retired with `replaces`; `-drop-curated-venues` allows deleting curated venues), and the log lists what was removed. See "Applying a pack" in [../data/README.md](../data/README.md). See [../data/README.md](../data/README.md).

## Geo data (Google Maps)

Set up keys first: [../docs/google-maps.md](../docs/google-maps.md). Then, for a seeded city:

```sh
go run ./cmd/tool build-matrix -dry-run tokyo     # plan only: requests and billed elements
go run ./cmd/tool build-matrix tokyo              # fills app.area_travel_times
go run ./cmd/tool discover-venues -dry-run tokyo
go run ./cmd/tool discover-venues -categories cafe,park tokyo
```

- **`build-matrix`** computes travel times between every pair of the city's areas, for each of the city's `travel_modes`. Same-area pairs are stored as 0 minutes without an API call. Only walking and driving are calculated (no public transport). Walking is only requested for areas less than 4 km apart; driving uses typical, traffic-unaware times. Minutes are rounded up. Pairs with no route are left out. Rows older than 30 days are deleted (Google caching terms), so **rebuild each city at least every 30 days**.
- **`discover-venues`** runs a Nearby Search per area × venue category, for categories used by an activity enabled in the city. Only places whose **primary** type is one of the category's types are kept. Categories with a radius of 10 km or more are searched once from the city centre. An area with a **boundary** (`areas.boundary`, from its city pack) is searched over all of it: one circle covering it, split into seven smaller ones wherever a search comes back full (20 places), down to the category's radius, coarse to fine across every area until `-max-requests` (default 4,000) runs out (`geo.split`). Each place is assigned to the area whose boundary contains it, else its **nearest** area (`geo.Locate`); places a bounded search finds outside every area are dropped. Stored as `google_place_id` + category. Re-running only bumps `last_seen_at`; curation status is kept.

## Plans, signups and events

A **plan** (`app.plans`) is open for signups in rounds, each with a window (default 14 days) and a signup deadline. **Signups** (`app.plan_signups`, with `plan_signup_slots` for a custom weekly pattern and `plan_signup_unavailable` for blocked-out dates or occasions) are the people waiting for the current round. Scheduling a round creates an **event** (`app.events`, one per round) with one or more **groups** (`app.event_groups`), each inviting people (`app.group_members`: invited → confirmed/declined, confirmed → dropped). Invited people leave the signups; the rest roll over to the next round. A person is in at most one group per event (enforced by the database). Each plan names its venues when it opens (`venue_place_id`, `follow_up_venue_place_id`; approved venues first, never rejected ones, otherwise random so one café isn't in every plan); the groups of an event share them, and `event_groups.venue_place_id` is only for a group sent elsewhere. Only Google place ids are stored. Plans close as `done`, `no_group` or `withdrawn`.

**The worker** (`make worker`) runs a pass per city every hour (`plans.Runner`, timing in `plans.Timing`):

- **Failure policy** (doc comment on `plans.Runner.Match`; the same in `crews.Runner.Pass` and the notifier): an *item* is a plan, an event group, a crew or a notification. One that fails is logged with its id, reported to Sentry and counted in its stage's `Failed`; the pass carries on. Each item commits in its own transaction and counters go up only after that commit, so a rollback never over-counts. The job returns an error (River retries it) only for a *setup* failure (the city or its items can't be loaded, the database is down) or when *every* item of a stage failed; some items failing is success, with `Failed > 0` in the report and the log line. The stages stay in order: a setup failure in settle (or loading the city) skips schedule and suggest, whose inputs would be wrong. Meeting places and routes are best effort: their errors are logged, never fail the job. A cancelled context (River timeout, shutdown) stops a pass with its error and counts nothing as failed. Suggest errors only when every suggestion it tried to store hit a database error: walks the composer couldn't make aren't counted, so a model outage doesn't retry the paid composer. If schedule or suggest fails outright, the stale-route cleanup (Maps caching terms) still runs before the job errors. `Match` loads the city once, after settling, with every activity: Schedule uses them all (a plan opened for a season keeps its round), Suggest keeps those in season in its round's month (`City.InSeason`).
- **Queues, time and attempts** (`internal/worker`): `notify` (1 worker: `send_notifications`), `passes` (2: `match_all`, `match_city`, `crews_city`) and `maintenance` (1: `refresh_maps`, `refresh_maps_city`, `retention`, `remove_suspended` and the admin jobs `apply_city_pack`, `discover_area_venues`), so a long city pass never delays a push. Each kind sets its queue and `MaxAttempts` in `InsertOpts` and its time limit in the worker's `Timeout` (River's defaults, a minute and 25 attempts, fit none): `match_city` 25 min × 3 (the next hourly pass retries anyway), `crews_city` 5 min × 5, `send_notifications` 2 min × 3, `match_all`, `refresh_maps` 1 min × 3, `refresh_maps_city` 10 min × 3, `retention` 5 min × 3, `remove_suspended` 2 min × 10 (every step is safe to repeat; unique per person), `apply_city_pack` 10 min × 1 (the seed commits before Google is asked, so a retry would report an empty apply; unique per city and pack hash), `discover_area_venues` 10 min × 2 (unique per city and area). The admin jobs record their result or failure as the job's output for `GetAdminJob` (`internal/adminjobs`). River's `default` queue is still served (1 worker) for jobs the previous release left in it; drop it once `select count(*) from river.river_job where queue = 'default' and state in ('available','retryable','scheduled','running')` is 0. The walk budget comes from the job: Gemini's 5 minutes is a cap on one call, the call also stops at the job's deadline, and `Suggest` starts no walk, and `Compose` no retry (`walks.ErrNoBudget`), with less than `walks.MinBudget` (6 minutes) left; a call already running ends at the deadline. The pass then starts no further round; it leaves the walks for the next run and counts them in `SuggestReport.Deferred` (`suggest_deferred` in the log), not as a failure.
- **Retention** (`retention`, daily, also on start): deletes `app.notifications` rows older than 30 days that were sent or have used their 5 attempts (unsent rows with attempts left stay), and the messages of crews whose `closed_at` (set for both `lapsed` and `closed` crews) is more than 30 days past; a member leaving an active crew deletes nothing. Both go in batches of 1000, so the job never holds a long lock, and the counts are logged (`notifications_deleted`, `crew_chat_messages_deleted`). The crew-chat delete uses `crew_messages_crew_idx`; no index covers old finished notifications (the pending index leaves them out), so each batch scans the push-queue table, which holds at most 30 days of rows.
- **Travel-time refresh** (`refresh_maps`, daily, also on start, queues a `refresh_maps_city` per city; one failing doesn't affect the others): `geo.Refresh` rebuilds a city's matrix once it's 25 days old (`geo.RefreshAge`), replacing it whole so nothing outlives the 30-day Maps caching limit; without a Maps key it returns `geo.ErrNoRouter` and deletes nothing (the fan-out skips the pass and logs an error; production can't start without the key).
- **Meeting places** (`Runner.RefreshMeetingPlaces`, in each city pass before routes): for plans whose first activity has no venue (a photo walk), one Places Nearby Search near the area's centre, a station within 1 km and otherwise a park within 1.5 km, once per plan. Only the place id is stored (`plans.meeting_place_id`); the plan's steps then start with a "Meet here" stop whose name and address are fetched live, and its route starts there. Nothing happens without a Maps key.
- **Walks** (`Runner.Suggest` with a `walks.Composer`): a suggestion for a walking activity (one with a `walk_theme`) is composed before it opens, up to 4 per pass at once; the plan stores its title and summary (English, translated on demand), its stops in `app.plan_stops` (place id, role, minutes, note, walk from the previous stop) and its route. A walk that can't be composed isn't opened: matching is asked again for the next best plan, and the area and activity rest for 7 days (`app.walk_failures`). Model or Maps errors don't rest. Composed walks never get the old kind of meeting place; at scheduling every stop must be open from arrival to departure. The city pass may take up to 25 minutes (`MatchCityTimeout`).
- **Walk benchmark** (`tool walk-bench`, no database): compares proposers before changing the production model or prompt. `run -dry-run` lists the walks and estimated cost first; then `run` (resumable; `-sample 12 -reps 1` for a pilot, `-cases`, `-variants`, `-prompt file`, `-activities file` to try other themes), `judge`, `review` (writes `review.html` to fill in: each plan links to its walking route through every stop in Google Maps, and embeds it when `GOOGLE_MAPS_EMBED_API_KEY` names a key with the Maps Embed API; re-running keeps the pairs so answers stay valid; then `report -human review_answers.json`), `report` (writes `report.md`). Needs `GOOGLE_MAPS_API_KEY` and `GOOGLE_GEMINI_API_KEY`. Claude runs by default through the Claude Code CLI on your Claude subscription (`claudecode:` variants: sign in with `claude` once; each call runs in an empty directory with tools, settings and MCP off, never with an API key); `claude:` variants and judges use the API and need `ANTHROPIC_API_KEY`. Confirm a CLI winner on the API before switching production. Keep run directories out of the repo (they're large); commit only conclusions to the roadmap.
- **Plan routes** (`Runner.RefreshRoutes`, in each city pass after Suggest): the walk between a plan's two venues (or its meeting place and the follow-up's venue) from the Routes API, stored on the plan (encoded polyline and seconds) for its map and the timeline's walking time; computed when a plan opens, recomputed at 25 days, cleared at 30 (Maps caching terms), only for plans still open or with an event to come.
- **Opening hours** (in **Schedule**, below): before a round is saved, the plan's venues are checked (Place Details hours, once per venue per pass): the activity's venue must be open at the start and 90 minutes in, a follow-up's 2–3 hours after the start (activities have no stored duration). A closed time is taken out of the window and the engine schedules again; a venue closed for good (or until further notice) withdraws the plan, and a permanently closed one is marked `rejected` so it's never picked again. Lookup failures don't block scheduling.
- **Push notifications** (`notifications.Notifier`, with the text written by `plans.NotificationRenderer` and `crews.NotificationRenderer`, a `send_notifications` job every minute): the changes that notify people write rows to `app.notifications` in the same transaction (an outbox: invited when a round is scheduled; group confirmed, at quorum or at the deadline; group cancelled; a plan closed without a group, to whoever was still waiting, with `planId` instead of `eventId` so the app opens the feed; "How was it?"; crew offered, formed and plan suggested, with `crewId`, titled with the crew's name), and the job sends them through Expo (`internal/push`) to every device the person registered: the plan's title, then a line from the UI catalogue in their language (`push.*` keys; no dates, which Go can't format per language). Tokens Expo reports as `DeviceNotRegistered` are deleted; if Expo can't be reached, the batch is retried on later passes (5 attempts); if it fails partway through, the messages Expo had already accepted are marked sent (with their tickets) and only the rest are retried, so nobody is pushed twice. The same job then checks **receipts** for pushes sent at least 15 minutes ago (`app.push_tickets`, kept a day): `DeviceNotRegistered` there deletes the token too, other refusals are logged.

0. **Settle** (which also deletes group chats 30 days after their event) groups whose confirmation deadline has passed: confirmed with at least `min_attendance`, otherwise cancelled; the people who had confirmed a cancelled group go back on the plan's waiting list (if it's still open), and an event with no group left is cancelled. Events whose date has passed are marked `done`. Once feedback opens (3 h after the start), everyone who went ahead with a group is sent "How was it?" (`event_feedback`), once per event.
0b. **Crews** (`crews.Runner.Pass`, the `crews_city` job queued after matching; one crew failing doesn't stop the rest, and the job then fails and retries): decide offers that everyone answered or that ran out; post a plan suggestion to active crews due one (a day after forming, then weekly); then offer new crews from `matching.FindCrews` over the city's met pairs, mutual picks, blocks and crew aversions, skipping sets offered before and crews overlapping an existing one on the same basis.
1. **Schedule** every open plan, most signups first (each event blocks its occasion for the people invited). Occasions start 2 days from today (time to confirm). Ready plans get an event; at the signup deadline (7 days into the 14-day window) the round goes ahead with whatever groups can form, or the plan closes as `no_group`. People not placed roll over to the next round, which starts in the same transaction; a plan with nobody left closes as `done`. A plan whose activity was disabled closes as `withdrawn`. Invitees answer by the start of the day before the event (local time). Events start at a set time for their part of the day (`Timing.BlockStarts`: 10:00, 14:00, 18:30 local), and their meeting point is shown to confirmed people from 24 hours before.
2. **Suggest** new plans up to the city's cap, with the activities in season in the month the round starts. Plans that closed as `no_group` in the last 14 days count as open, so they don't reopen the next hour.

Not done yet: chat, push notifications, the travel-matrix refresh and AI-written plan text.

## Matching

`internal/matching` runs **plan first, time second**: suggest plans without a date, rank them for each person, then schedule a plan once its signups can make a good group. The caller (the M6 worker and API) loads everything (users, approved venues, activities enabled and in season, the fastest travel time per area pair, open plans and signups, mutual picks and blocks) and stores the results; the engine itself does no I/O. **Relations** (M7): `MutualLinks` links two people who picked each other after outings, with the lower of their two pick return rates ((returned + 2) / (made + 2)), so someone who picks everyone counts for less; a report or a "rather not" blocks the pair for good. `FindCrews` finds crews in the graph of people who've met (maximal cliques, Bron–Kerbosch), keeping members with a mutual pick inside and a shared liked activity or home area.

1. **`Pools`:** every area is a candidate meeting place. A person joins each area they can reach within `max_travel_min`, in each language they speak fluently. Two-language pools exist only for the city's `language_pairs`, and anyone fluent in either language joins.
2. **`Suggest`:** for each pool, activities with a venue in the area (or needing only a meeting point) and an audience of at least `min_audience` people who want them and are usually free at a part of the day they suit (`activities.blocks`). Ranked by demand (love 2, like 1, open to try 0.5; × 0.3 if over budget) × venue choice, then taken best first across the city: not already open, at most `plans_per_pool` per pool, the same activity in a shared language at least `plan_spacing_min` minutes apart, at most one open plan per `users_per_plan` people. A non-conversational activity gets a food follow-up.
3. **`Feed`:** every open plan for one person, in levels (top = love, good = like, maybe = open to try, low = no preference or too far, not-for-you = doesn't speak its language) for the feed's order and the map's colours. Within a level: interest, momentum (signups so far), fit with their usual availability, then distance. A plan people they get on with (mutual picks) signed up for moves up a level and gains `weights.friends`; `ListFeed` returns the count as `friendsInterested`, never who.
4. **Signups:** `Signup.Pattern` is the weekly slots that suit them for this plan (nil = profile availability) and `Unavailable` the dates or occasions they can't do. The caller adds the occasions of events they're already going to.
5. **`Schedule`:** for each occasion in the plan's window, form groups from the signups free then (greedy, then local search: fill, replace, swap, spread small groups); keep the best occasion, ties to the earliest. Ready when a group reaches its target size; groups below the preferred size wait for the next round. With `force` (the signup deadline) every group that can form goes ahead. Each group invites its target plus `extra_invites`; `Quorum` confirms straight away and `MinAttendance` (2) is the fewest it can go ahead with at the confirmation deadline.

Hard rules (`Violation`): no blocked pairs; same-gender-only is respected; at least 2 people (`min_group_size`). There's no cap on friends: the score's friendship part (`friendship`) rewards clusters of people who picked each other. Removing people never breaks them, so they still hold after declines.

Preferences (in the group score, so the engine avoids them when it can but would rather go ahead than leave someone out): groups of at least 3 or the activity's own minimum (`preferred_min_size`, weight `min_size`); nobody the only woman or only man (weight `balance`; nonbinary and unspecified exempt). The only language rule is the event's: everyone speaks its primary or secondary language.

Settings are in `matching.Config` (`DefaultConfig`). A city overrides any of them with JSON in `app.cities.matching`, e.g. `{"language_pairs": [["ja", "en"]], "users_per_plan": 15, "weights": {"mutual": 2}}`. Unknown keys are rejected.

```sh
make sim                                           # 500 synthetic users per city pack
make sim ARGS="-users 1000 -seed 2 -config '{\"language_pairs\":[[\"ja\",\"en\"]]}'"
```

The simulator runs the whole flow on synthetic users: suggest, signups from each person's feed (with varied availability), then scheduling (ready plans first, then the rest at their deadline), never double-booking anyone. It reports plans, signups, scheduling, group sizes, pairs, gender balance, who got invited by gender and language, and any rule violations, which fail the run. `go test ./internal/matching/sim` runs it for every pack in CI. The activities come from `plans.Activities`, the Go twin of the worker's `ListMatchingActivities` query (a database test keeps them agreeing). It does not model the worker's rounds, waiting list, relations, suspensions, venue review or notifications (see `sim.Run`).

Tests must never call paid external APIs. Run the same checks locally with `make test-db`: it starts a throwaway container of that image of its own (named after the worktree, on a free port; multi-arch, so native on Apple silicon), runs `scripts/db-checks.sh` (the script CI's `backend` job runs, so the steps and package list exist once) and removes the container afterwards, also on failure or Ctrl-C. It needs Docker, strips any hosted `DATABASE_URL` (from `.env*` or `ENV_FILE`) and replaces it with the container's, and `db-checks.sh` refuses a non-local host, so parallel worktrees don't clash. The tests create and remove their own throwaway cities, activity and users.

```sh
make gen   # from root: buf (Go + TS + docs), sqlc, and the UI-text copy (internal/uistrings/en.json)
```

The code generators are pinned as `tool` directives in `go.mod`, and `../go.work` makes `go tool` work from the repo root.
