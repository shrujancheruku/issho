# backend

The Go backend for Issho: a modular monolith serving a ConnectRPC API. It uses Postgres (Supabase) through pgx and sqlc, and goose for migrations. Architecture notes are in [../docs/architecture.md](../docs/architecture.md).

## Layout

| Path | Contents |
|---|---|
| `cmd/api/` | API server: wires config, DB pool, the JWKS verifier and handlers, then serves HTTP/1.1 and h2c on `API_ADDR` |
| `cmd/worker/` | Background jobs on River (`internal/worker`): starts the River client and stops it gracefully on SIGINT/SIGTERM |
| `cmd/tool/` | Ops CLI: `migrate <goose command>`, `seed [-catalog file] [-venue-categories file] <citypack.json>...` (also applies catalogue merges: `replaces`), `build-matrix [-dry-run] <city>`, `discover-venues [-dry-run] [-categories ids] [-max-requests n] <city>`, `area-boundaries [-threshold deg] <citypack.json>` (areas' outlines from OpenStreetMap by `osm_id`; no database; `make boundaries CITY=…`), `email-templates [-source file] [-out dir] [-config file]` (sign-in emails in every language of `supabase/templates/source.json`, machine-translated; needs `GOOGLE_TRANSLATE_API_KEY`), `simulate [-users n] [-seed n] [-month n] [-config json] [-seeds n] [-thin x] [-variety x] [-neutral x] <citypack.json>...` (no database needed; `-seeds` averages that many cities, the other three set how simulated people respond to a plan's shape), `set-admin [-revoke] <email>` (the admin SPA's role, below), `set-translator <email> <ja,es,...>` / `set-translator -revoke <email>` (the translation editor only, for those languages), `ui-strings <apps/mobile/src/i18n>` (checks and stamps the UI text's human versions and checks the notes; run by `make gen`), `translate-compare [-langs ja,es,pl,zh] [-out file.json]` (Google and Gemini on every UI string, side by side, for review; stores nothing; needs both keys), `ui-bundle -api <url>` (`make ui-bundle`: the city packs' languages as that API serves them, bundled into the app; no database) |
| `internal/platform/config` | Environment variables → `Config` |
| `internal/platform/db` | pgx pool and goose migration runner |
| `internal/platform/auth` | Supabase JWT verification (JWKS) and the Connect auth interceptor; `Require` and `RequireAdmin` for handlers |
| `internal/platform/i18n` | Language rules: which primary/secondary pair to show (`ForApp`, events included), what to display from resolved text (`Pair`), ISO 639-1 validation |
| `internal/translate` | Text in any language on demand: stored text → `app.translations` cache → `Translator`, with in-flight de-duplication, a bounded wait and background completion; `Prefill` for content that must exist in given languages (events) |
| `internal/translate/google` | `Translator` using Google Cloud Translation Basic (v2): plain-text mode, batches of ≤ 128 strings and ~5,000 characters |
| `internal/translate/gemini` | `Translator` using Gemini (`gemini-3.8-flash`), the default: each string's context plus the translation guide (`internal/translate/guide.md`: voice, the product's name, terms such as crew, register per language), 40 strings per call, 4 calls side by side. Editing the guide doesn't redo cached translations: delete the unreviewed `app.translations` rows of the languages concerned |
| `internal/translate/translators` | Picks the translator from `TRANSLATOR` for the API, the worker and the tools |
| `internal/platform/googleapi` | Shared transport for key-based Google APIs (Maps, Translation): key in a header, retries on 429/5xx |
| `internal/platform/sentry` | Error reporting when `SENTRY_DSN` is set, a no-op otherwise: `Report`, `Handler` (panics), `JobErrors` (River) |
| `internal/platform/errs` | Connect interceptor: logs unexpected errors and returns a generic `internal error` (no leaked details); `Invalid` for `invalid_argument` errors |
| `internal/platform/supabase` | Supabase admin API client (account deletion, the admin role), using the secret key |
| `internal/moderation` | `ModerationService`: the admin SPA's moderation queue (reports, flags, crew leave reasons) and suspensions; admins only |
| `internal/health` | `HealthService` |
| `internal/identity` | `IdentityService`: app account on top of Supabase users (get, delete) |
| `internal/catalog` | `CatalogService`: activity catalogue with city overrides, cities and areas, language names (CLDR via `golang.org/x/text`) |
| `internal/profile` | `ProfileService`: the caller's own profile (validation in `validate.go`, one-transaction save in `service.go`); `ConductVersion` |
| `internal/tagging` | Free-text interests → suggested activities (`Service.Suggest`: input limits, city catalogue, drops unknown ids, keeps the strongest level per activity) behind the `Tagger` interface |
| `internal/platform/gemini` | Shared Gemini client on Agent Platform: `generateContent` with a system prompt, a user turn and a JSON response schema; returns the answer text, `ErrDeclined` for blocked or safety-stopped answers. Used by tagging and walks |
| `internal/walks` | **Walk composer**: a `Proposer` (the model) proposes a walk from its own knowledge (meeting place, 4–7 stops on the theme, a place to finish), then Places Text Search checks every place (exists under the model's name, compared loosely in memory since Text Search returns its nearest match for anything; open; within 3 km of the area's centre; the right kind for a station, café, bar, temple or shrine; not a duplicate), failing stops are dropped, Routes walks them in the best order (`optimizeWaypointOrder`), an outlier stop more than 20 min away is dropped, and the whole walk must take 2–4 hours with at most 100 min walking. A walk that fails goes back to the model once with the problems named (its own place names and our rules only, never Google content), then is `*Rejected` |
| `internal/walks/claude` | `Proposer` using Claude (Anthropic Go SDK): same prompt and schema as Gemini (`walks.SystemPrompt`, `walks.ProposalSchema`), structured outputs, effort per variant, no tools and no refusal fallback (a benchmark must measure the model it names) |
| `internal/walks/bench` | **Walk benchmark**: 38 cases (`cases.json`: every walking theme, Tokyo and Austin, known, mid, quiet and hard areas, several months and parts of the day) run through the production composer for each variant (`provider:model[:effort]`), with reps; results, errors and traces as JSONL; blind pairwise judging by a jury (one Claude, one Gemini) in both orders on six criteria (theme, flow, social, notes, local, overall) plus doubted claims; a blind human review sheet whose answers calibrate the judges; a Markdown report with 95% intervals. Judges see only model-written text, never Google content or Routes times. `tool walk-bench`, below |
| `internal/walks/gemini` | `Proposer` using `gemini-3.8-flash` (medium thinking, 5 min per attempt) with no grounding: grounded answers may only be shown to the person who asked, not stored. `eval_test.go` composes real walks for review |
| `internal/tagging/gemini` | `Tagger` using Gemini (`gemini-3.5-flash-lite`) on Google Cloud's **Agent Platform** (formerly Vertex AI): `generateContent` over REST with a Google Cloud API key, via `internal/platform/googleapi`. A response schema that only allows the city's activity ids, low thinking, 20 s deadline; blocked or safety-stopped answers count as "no suggestion". `testdata/eval.json` + `eval_test.go` is the multilingual eval set |
| `internal/emailtemplates` | Builds the multilingual Supabase sign-in email templates and subjects from one English source: branches on `.Data.lang`, English fallback, escaping and checks that no translation can break the template or `config.toml` |
| `internal/uistrings` | `UIService`: the app's UI text in any language. `en.json` and `human/` are copies of `apps/mobile/src/i18n/` made by `make gen`; only those strings are translated. Human versions (`human.go`) replace single strings when they were written for today's English; the rest is machine-translated |
| `internal/translations` | `TranslationService`: the admin SPA's translation editor, for admins and translators (their languages only). UI strings are saved as human versions through **one rolling pull request per language** (`translations/<lang>-<time>` branches; each save is one commit with both copies of `human/<lang>.json`, retried once if the branch moved); catalogue text (activity and city names) is corrected in `app.translations` |
| `internal/cities` | City-pack, catalogue and venue-category JSON formats; validation and seeding |
| `internal/maps` | Provider-neutral geo interfaces (`Router` for travel-time matrices, `PlaceSearcher` for nearby places) |
| `internal/maps/google` | Google implementation: Routes API (Compute Route Matrix), Places API (New) Nearby Search and Place Details (`Details`: localised name, short address, Maps link, location) over REST, with retries on 429/5xx. `placetypes.txt` is a snapshot of valid place types. |
| `internal/matching` | The matching engine (M4), pure: no I/O, deterministic. `Suggest` (plans without a date), `Feed` (plans ranked for one person, with map levels), `Schedule` (date and groups from signups); `Violation` checks a group's hard rules; `ParseConfig` reads a city's overrides. See [Matching](#matching) |
| `internal/matching/sim` | Synthetic users for any city pack (estimated travel times, made-up venues, guessed signup behaviour); runs suggest → signups → schedule and checks the output |
| `internal/worker` | River jobs: `match_all` (periodic, hourly, and once on start) queues a `match_city` pass per city, which runs `plans.Runner.Schedule` then `Suggest`. One pass per city is queued or running at a time (unique jobs). River's tables live in the `river` schema |
| `internal/chatws` | Group chat over WebSocket (`/ws/chat`): a `Hub` holding one connection per process listening on `chat` and `chat_typing` (reconnecting after errors) that wakes the sockets open on a group and passes on typing notices, and the handler (first-message auth, access via `plans.Service.ChatMessages`, catch-up then live messages, typing notices both ways, pings every 30 s). The API's request contexts end on shutdown, which closes the sockets (`Shutdown` doesn't track hijacked connections) |
| `internal/plans` | `PlanService` (`handler.go`, `service.go`: the caller's feed, a plan, signing up and withdrawing), `Runner` (the worker's passes: `Schedule` checks every open plan, `Suggest` opens plans up to the city's cap) and `LoadCity` (a city's matching input from the database), plus the store. Stores open plans, signups and scheduled events (M6) and converts them to and from `internal/matching`'s types: `Create`, `ListOpen` (with signup counts), `SaveSignup` (times replaced wholesale), `LoadSignups` (adds the occasions people are already invited to, so nobody is double-booked), `SaveEvent` (event, groups and invitations; invited people stop waiting), `NextRound`, `Close`. Saves lock the plan row, so a signup lands either before a round is scheduled or in the next one |
| `internal/crews` | `CrewService` (`handler.go`, `crews.go`: the caller's crews, answering an offer, crew chat, leaving with a reason, reporting a member), `Runner.Pass` (the worker's crew pass, below) and `Service.RemoveFromAll` (suspensions). Uses `internal/plans` for cities and report rules |
| `internal/chat` | Chat storage shared by event and crew chats: when a chat opens and closes, message limits and cleaning, posting with `NOTIFY chat`, deleting old event chats |
| `internal/testfixture` | A throwaway city, area, activity and users for integration tests, removed afterwards; shared so packages that import `plans` can test without an import cycle |
| `internal/geo` | Builds a city's travel-time matrix and venue list through the `maps` interfaces, and stores them |
| `db/migrations/` | goose SQL migrations (embedded via `db/embed.go`) |
| `db/queries/` | sqlc queries |
| `gen/` | **Generated.** `gen/issho` (protobuf/Connect), `gen/dbgen` (sqlc). Don't edit; run `make gen`. |

## Configuration

| Variable | Required | Example (local) | Notes |
|---|---|---|---|
| `DATABASE_URL` | yes | `postgres://postgres:postgres@127.0.0.1:54322/postgres?sslmode=disable` | Supabase local DB. In production, use the **session pooler** (port 5432) or the direct connection, with `sslmode=require`. **Not** the transaction pooler (port 6543): pgx's prepared statements and River's LISTEN/NOTIFY don't work through it. |
| `WORKER_DATABASE_URL` | worker only; falls back to `DATABASE_URL` | same as `DATABASE_URL` | The worker's connection. River needs LISTEN/NOTIFY: direct connection or session pooler only. |
| `GOOGLE_MAPS_API_KEY` (worker) | no | (empty) | The worker uses it to rebuild travel times before the 30-day Maps limit and to check venues are open before scheduling. Without it, travel times past 30 days are deleted (not rebuilt) and hours aren't checked. |
| `EXPO_ACCESS_TOKEN` | worker; only with enhanced push security | (empty) | **Secret.** Sent to Expo's push service when the Expo project requires it. |
| `GOOGLE_TRANSLATE_API_KEY` (worker) | no | (empty) | With `TRANSLATOR=google`, the worker uses it for push notifications in each person's language. |
| `SUPABASE_URL` | yes | `http://127.0.0.1:54321` | The JWKS is fetched from `$SUPABASE_URL/auth/v1/.well-known/jwks.json`. The token issuer must be `$SUPABASE_URL/auth/v1`. |
| `API_ADDR` | no | `:8080` | Listen address |
| `SUPABASE_SECRET_KEY` | no | `SECRET_KEY` from `supabase status` | **Server-only secret.** Enables admin calls (account deletion). Without it, `DeleteAccount` returns `failed_precondition`. Never commit it; see [secrets](../docs/secrets.md). |
| `GOOGLE_MAPS_API_KEY` | for `tool build-matrix` / `discover-venues`; optional for the API | (empty) | **Server-only secret**, restricted to the Routes and Places APIs. Not needed for `-dry-run` or tests. The API uses it for venue names and addresses on plans (Place Details, fetched live); without it, plans show no venue names. See [google-maps](../docs/google-maps.md). |
| `GITHUB_TOKEN` | no | (empty) | **Server-only secret** (see [secrets](../docs/secrets.md)): a fine-grained token for the repository with Contents and Pull requests write. Enables the admin SPA's city-pack editor (`CityPackService`), which proposes packs as pull requests, and the translation editor's saves (`TranslationService`); without it, those calls (except `ListCityPacks` and the translation editor's reads) return `failed_precondition`. With it, the API also reads the human versions of the UI text on `main` every 5 minutes, so merged translations are served without a deploy. |
| `SENTRY_DSN`, `SENTRY_ENVIRONMENT` | no | (empty), `development` | Error reporting for the API and the worker (`internal/platform/sentry`): unexpected RPC errors (not the ones handlers return on purpose), HTTP handler panics, and failed or panicking jobs. No personal data (IPs, headers). Empty = off. |
| `SENTRY_TRACES_SAMPLE_RATE` | no | `1` | Share of API requests traced (0 to 1) when Sentry is on: a transaction per request with a span per query (by its sqlc name), connection wait and outside API call (method, host and path; no headers or query string). Requests the app traced are always traced. Health checks, CORS preflights and the chat socket never are. The worker isn't traced. |
| `GITHUB_REPO`, `GITHUB_API_URL` | no | `shrujancheruku/issho`, `https://api.github.com` | Where the city packs live (another API address for GitHub Enterprise or a local fake). |
| `GOOGLE_GEMINI_API_KEY` | no | (empty) | **Server-only secret**: a Google Cloud API key for Agent Platform (created in Agent Platform; it starts `AQ.`). It only works on `aiplatform.googleapis.com`, not the Gemini Developer API (`API_KEY_SERVICE_BLOCKED`). Enables interest suggestions (`CatalogService.SuggestActivities`); without it, that RPC returns `failed_precondition` and the app says suggestions aren't available. **The worker** uses it too, with `GOOGLE_MAPS_API_KEY`, to compose walking plans; without both, no walks are opened. With the default `TRANSLATOR`, it's also the machine translator, for the API and for the worker's push notifications; without it, text is shown in the languages already stored. |
| `TRANSLATOR` | no | `gemini` | The machine translator: `gemini` (`GOOGLE_GEMINI_API_KEY`; reads each string's context and the translation guide) or `google` (Cloud Translation Basic, `GOOGLE_TRANSLATE_API_KEY`, kept for comparison). The worker reads it too. Switching doesn't redo cached translations; see the ROADMAP. |
| `GOOGLE_TRANSLATE_API_KEY` | no | (empty) | **Server-only secret**, restricted to the Cloud Translation API. Used for translation only with `TRANSLATOR=google`. Without it, text is shown in the languages already stored (English, local names, cached translations). See [google-maps](../docs/google-maps.md#6-cloud-translation). |
| `ALLOWED_ORIGINS` | no | `https://admin.example.com` | Comma-separated browser origins. **Empty = no browser origins allowed.** |

Local defaults are in `../.env.example`: `export $(grep -v '^#' ../.env.example | xargs)`.

## Run

```sh
supabase start                 # from repo root; see ../supabase/README.md
make migrate-up seed api       # from repo root
make worker                    # background jobs (another terminal)
```

Or from this directory: `go run ./cmd/tool migrate up`, `go run ./cmd/tool seed ../data/citypacks/tokyo.json`, `go run ./cmd/api`.

### Container image

`Dockerfile` builds one image with all three binaries (`api` by default, `worker`, `tool`) and `data/` for seeding; Kamal deploys it ([../docs/deploy.md](../docs/deploy.md)). Build it from the repository root:

```sh
docker build -f backend/Dockerfile --build-arg VERSION=$(git rev-parse --short HEAD) -t issho-backend .
DB='postgres://postgres:postgres@host.docker.internal:54322/postgres?sslmode=disable'   # the local stack, from a container
docker run --rm -e DATABASE_URL="$DB" issho-backend tool migrate status
docker run --rm -p 8095:8080 -e DATABASE_URL="$DB" -e SUPABASE_URL=http://host.docker.internal:54321 issho-backend
docker run --rm -e DATABASE_URL="$DB" issho-backend worker
```

The runtime image is distroless (no shell, non-root); `.dockerignore` keeps everything but `backend/` and `data/` (and any env file) out of the build. The Go module and build caches are BuildKit cache mounts, so a rebuild after a code change only recompiles what changed, provided BuildKit's garbage collector keeps them: if every build recompiles from scratch, raise its limit (Docker's `builder.gc` setting; on OrbStack, `~/.orbstack/config/docker.json`). CI builds it on every PR.

## API endpoints

The full reference, generated from the proto comments, is in **[../docs/generated/api.md](../docs/generated/api.md)**. All RPCs are `POST /<package>.<Service>/<Method>` with a JSON body (`Content-Type: application/json`) or binary protobuf.

| Endpoint | Auth | Purpose |
|---|---|---|
| `POST /issho.v1.HealthService/Check` | public | Database ping and build version |
| `GET /up` | public | `200 ok` when the database answers, `503` otherwise. Plain HTTP for kamal-proxy's health check, which only does GETs. |
| `POST /issho.v1.IdentityService/GetMe` | bearer | Returns (and lazily creates) the caller's account: `onboarded` and, once onboarded, the display languages and the home city (`city_id`, so the app can load the city's catalogue without waiting for `GetProfile`). `unauthenticated: account deleted` for tokens of deleted users. |
| `POST /issho.v1.IdentityService/DeleteAccount` | bearer | Permanently deletes the caller (Supabase auth user → cascades to app data). Safe to retry. |
| `POST /issho.v1.UIService/GetStrings` | public | The app's UI text in `language` (any ISO 639-1 code): human versions where there are current ones, the rest machine-translated on demand and cached. Strings still being translated, or whose `{placeholders}` didn't survive, are left out (the app shows English); `complete: false` means ask again later. `catalog_version` is a hash of the text returned; pass it back as `known_version` and an unchanged, complete catalogue comes back as `unchanged: true` with no strings. Public because the sign-in screens need it. |
| `POST /issho.v1.ProfileService/GetProfile` | bearer | The caller's profile and the current code-of-conduct version. `not_found` before onboarding. |
| `POST /issho.v1.ProfileService/SaveProfile` | bearer | Creates or replaces the whole profile (languages, availability and activity preferences included) in one transaction. `invalid_argument` names the field (e.g. `birth_year: must be at least 18`); `failed_precondition` if `GetMe` hasn't created the account. |
| `POST /issho.v1.CatalogService/ListCities` | bearer | Cities with their areas (with each area's centre, `lat`/`lng`, for the map of plans). City names in `locale` + `secondaryLanguage` (translated); area names only as stored (English plus a real local name such as 吉祥寺), never machine-translated. |
| `POST /issho.v1.CatalogService/ListLanguages` | bearer | Every ISO 639-1 language: its own name (`autonym`) and its name in `locale`, from CLDR. |
| `POST /issho.v1.CatalogService/SuggestActivities` | bearer | Suggests activities offered in `cityId` from free `text` (any language, 1–500 characters), each with an interest level, using Google's Gemini API. Suggestions only: the app shows them for the person to confirm. Empty list = nothing matched (or the model declined). `failed_precondition` without `GOOGLE_GEMINI_API_KEY`. |
| `POST /issho.v1.PlanService/ListFeed` | bearer | Every open plan in the caller's city, best for them first (`matching.Feed`), each with a `title` summarising the outing ("Climbing and bouldering, then lunch or dinner out", composed in English and translated into the caller's two display languages; area names are left out because they're never machine-translated), a `level` (top/good/maybe/low/not-for-you) for the feed and map, the signup count (never who), travel minutes from their home area (-1 = no route), the round's window and signup deadline, and `signedUp`. Ids only: names come from `CatalogService`. `failed_precondition` before onboarding. |
| `POST /issho.v1.PlanService/GetPlan` | bearer | One open plan as in the feed (or one in the caller's city **closed in the last 14 days**, unranked, with `closed_reason` and `closed_at`, so a push or link about it explains what happened), its `steps` (the activity, then any follow-up, each with its venue's Google name in both display languages, short address, Maps link and location, fetched live, plus the walk from the previous stop: Google's time when the route is known, else an estimate; for a **walk**, the meeting place, each stop and the finish, with `minutes` there and a `note` in both display languages), `routePolyline` (the walk through the venues, for the plan's map), a walk's `summary` in both languages, and the caller's `signup` (their weekly pattern and blocked-out dates) if they've signed up. `not_found` for unknown or closed plans and plans in another city. |
| `POST /issho.v1.PlanService/SignUp` | bearer | Signs up for a plan or replaces the times given before. An empty `pattern` means the profile's usual availability. `invalid_argument` for malformed times or dates outside the window; `failed_precondition` when the caller doesn't speak the plan's language; `not_found` once it's closed. |
| `POST /issho.v1.PlanService/Withdraw` | bearer | Removes the caller's signup. Safe to repeat. |
| `POST /issho.v1.EventService/ListMyEvents` | bearer | The caller's events from yesterday on (and older ones still waiting for their feedback), soonest first: title, date, start time, answer deadline, event and group status, their answer, how many confirmed (never who), and the meeting point once revealed; `feedbackFrom`/`feedbackUntil`/`feedbackGiven` for people who went ahead with their group; `checkInFrom`/`checkInUntil`, `revealAt` and `reportUntil`. The windows come from one place (`plans.Membership`), so the app reads them instead of copying the rules. |
| `POST /issho.v1.EventService/GetEvent` | bearer | One of the caller's events with its stops (as `GetPlan`) and, only if they confirmed, the first names of everyone confirmed in their group. `not_found` unless invited. |
| `POST /issho.v1.EventService/RespondToEvent` | bearer | `CONFIRM` (invited or declined → confirmed) or `DECLINE` until the deadline; `CANCEL` a confirmed place until the start. A group is confirmed as soon as `quorum` confirm; a cancellation below `min_attendance` sends it back to collecting answers, or cancels it after the deadline. `failed_precondition` when too late, cancelled or not applicable. |
| `POST /issho.v1.EventService/ListChatMessages` | bearer | The caller's group chat for an event (latest 100, or those after `afterId`), with when it's writable (`opensAt`, `closesAt`, `open`). Only for people who confirmed (`permission_denied` otherwise); empty before it opens. |
| `POST /issho.v1.EventService/SendChatMessage` | bearer | Posts 1–1000 characters while the chat is open (48 h before the start to 24 h after); `failed_precondition` otherwise. |
| `POST /issho.v1.EventService/CheckIn` | bearer | "I'm here": only for people who confirmed (`permission_denied`), from 30 min before the start to 3 h after (`failed_precondition` otherwise); again is fine. Check-ins count as attending and towards reliability (`ListMatchingUsers`: check-ins over confirmed places at finished events, prior of two). |
| `POST /issho.v1.EventService/GetFeedback` | bearer | The caller's feedback form (M7): the others in their group who confirmed (first names and an id, `cancelled` if they dropped), their earlier answer and picks, and when it's `open`. For anyone who confirmed, even if they cancelled since (to report someone); `permission_denied` otherwise. Open only to people who went ahead with their group, from 3 h after the start for 14 days. |
| `POST /issho.v1.EventService/SubmitFeedback` | bearer | Whether they went, the plan and group ratings (1–5, required when they went) and who they'd meet again and who they'd rather not be grouped with again (`avoid`; people who went ahead with the group; private; nobody in both). Replaces any earlier answer. Saying they went counts as attending, like a check-in. Afterwards their picks so far are checked with `matching.PickLean`, and a lean towards one gender opens an `app.moderation_flags` row. `failed_precondition` outside the window. |
| `POST /issho.v1.CrewService/ListMyCrews` | bearer | The caller's crews and open crew offers, newest first: status, what it's named after (`activityId` or `areaId`; the app composes "{name} crew"), the offer deadline, their answer, and members (first names, `accepted`, `me`). |
| `POST /issho.v1.CrewService/GetCrew` | bearer | One of them; `not_found` otherwise (declined, left, lapsed or closed). |
| `POST /issho.v1.CrewService/RespondToCrew` | bearer | Accept or decline an offer until it closes (the answer can change until then; `failed_precondition` after). Once everyone has answered it's decided at once: active with at least 3 who accepted (`crew_formed` push), otherwise lapsed. |
| `POST /issho.v1.CrewService/ListCrewMessages` / `SendCrewMessage` | bearer | The crew's chat (latest 100, or after `afterId`; 1–1000 characters), members only (`permission_denied`). Suggested plans are messages with a `planId`. Live over `/ws/chat` with `crewId` in place of `eventId`. |
| `POST /issho.v1.CrewService/LeaveCrew` | bearer | Leave with a reason (`UNCOMFORTABLE`, `NOT_INTERESTED`, `INACTIVE`, `TOO_MANY_MESSAGES`, `OTHER`) and optional details, stored in `app.crew_leaves`; the crew isn't told. A crew left with one member closes. |
| `POST /issho.v1.CrewService/ReportCrewMember` | bearer | As `ReportPerson`, for someone who is or was in the caller's crew. |
| `POST /issho.v1.EventService/ReportPerson` | bearer | Reports someone in the caller's group (`DATING`, `HARASSMENT`, `UNSAFE`, `NO_SHOW`, `OTHER`, optional details up to 1000 characters) until 30 days after the start; again about the same person and outing replaces it. The pair is never grouped again (`Relations.Blocked`). Stored in `app.reports` for the moderation queue (M8). |
| `POST /issho.v1.ReviewService/*` | bearer, **admin** | Plan review in the admin SPA (`plans.ReviewHandler`). `ListReviewCities` (review switch, draft and open counts) and `SetCityReview`; `ListReviewPlans` (a city's drafts oldest first, open or closed newest first; ### Authentication
- Clients send `Authorization: Bearer <Supabase access token>`.
- Tokens must:
  - be signed **ES256 or RS256** with a key from the project JWKS (HS256 is rejected)
  - have issuer `$SUPABASE_URL/auth/v1`
  - have audience `authenticated`
  - have an `exp` claim that hasn't passed
- **Deny-by-default:** every RPC requires auth unless it's listed as public in `cmd/api/main.go` (`HealthService.Check`, `UIService.GetStrings`).
- **Suspended accounts** (`app.suspensions`, set by `ModerationService.SuspendPerson`): `moderation.Gate` refuses every call from them with `permission_denied` / `account suspended`, except `IdentityService.GetMe` (which returns `suspended: true`, so the app shows a suspended screen), `DeleteAccount` and `PushService.UnregisterPushToken` (signing out). The chat socket refuses them too. The check keeps everyone suspended in memory, reloaded every 15 s (at once on the instance that made the change). Suspending also takes them out of their open signups, outings that haven't started (an invitation declined, a confirmed place cancelled, the group re-opening or cancelled as if they'd cancelled themselves) and crews (leaving an active one, which closes if one member is left; declining an offer): `plans.Service.RemoveFromUpcoming` and `crews.Service.RemoveFromAll`, both safe to repeat. Matching (`ListMatchingUsers`), crew offers (`ListCityMetPairs`) and push (`ListPushTokens`) leave them out while it lasts. Lifting doesn't put them back into anything.
- **Admins** are ordinary Supabase users with `app_metadata.admin = true` (only the service role can change `app_metadata`; `user_metadata`, which users can edit, is never read). Grant or remove it with `go run ./cmd/tool set-admin [-revoke] <email>` (needs `DATABASE_URL`, `SUPABASE_URL` and `SUPABASE_SECRET_KEY`; the person must have signed in once). It's carried in the access token, so it takes effect at the next token refresh (at most an hour; signing out and in applies it at once). Admin-only services are listed in `auth.AdminOnly` in `cmd/api/main.go`, so every RPC they have, new ones included, is covered; handlers check again.

## Migrations

```sh
go run ./cmd/tool migrate up        # apply all
go run ./cmd/tool migrate down      # roll back one
go run ./cmd/tool migrate status
```

- Write new files as `db/migrations/000NN_name.sql` with `-- +goose Up` / `-- +goose Down` sections. Wrap multi-statement blocks (`DO $$ … $$`) in `-- +goose StatementBegin/End`.
- goose records its versions in `goose.db_version`, in a schema of its own. Not `public`, which Supabase's Data API would expose. Not `app`, which migration 00001's Down drops. Older databases with `public.app_goose_db_version` are moved automatically on the next run.
- **River's tables** (the worker's job queue) are created by `00008_river.go` (`db/river.go`), a Go migration that runs River's own migrator up to `RiverVersion` in the `river` schema; Down drops the schema. When a River upgrade brings a new schema version, add a goose migration that migrates up to it, so goose stays the one owner of migration order.
- Supabase-only statements (the `auth.users` foreign key, revoking `anon`) are guarded with `IF EXISTS` checks, so the same migrations also run on plain Postgres in CI.

## Geo data (Google Maps)

Set up keys first: [../docs/google-maps.md](../docs/google-maps.md). Then, for a seeded city:

```sh
go run ./cmd/tool build-matrix -dry-run tokyo     # plan only: requests and billed elements
go run ./cmd/tool build-matrix tokyo              # fills app.area_travel_times
go run ./cmd/tool discover-venues -dry-run tokyo
go run ./cmd/tool discover-venues -categories cafe,park tokyo
```

- **`build-matrix`** computes travel times between every pair of the city's areas, for each of the city's `travel_modes`. Same-area pairs are stored as 0 minutes without an API call. Only walking and driving are calculated (no public transport). Walking is only requested for areas less than 4 km apart; driving uses typical, traffic-unaware times. Minutes are rounded up. Pairs with no route are left out. Rows older than 30 days are deleted (Google caching terms), so **rebuild each city at least every 30 days**.
- **`discover-venues`** runs a Nearby Search per area × venue category, for categories used by an activity enabled in the city. Only places whose **primary** type is one of the category's types are kept. Categories with a radius of 10 km or more are searched once from the city centre. An area with a **boundary** (migration 00027, from its city pack) is searched over all of it: one circle covering it, split into seven smaller ones wherever a search comes back full (20 places), down to the category's radius, coarse to fine across every area until `-max-requests` (default 4,000) runs out (`geo.split`). Each place is assigned to the area whose boundary contains it, else its **nearest** area (`geo.Locate`); places a bounded search finds outside every area are dropped. Stored as `google_place_id` + category. Re-running only bumps `last_seen_at`; curation status and tags are kept.

## Plans, signups and events

A **plan** (`app.plans`) is open for signups in rounds, each with a window (default 14 days) and a signup deadline. **Signups** (`app.plan_signups`, with `plan_signup_slots` for a custom weekly pattern and `plan_signup_unavailable` for blocked-out dates or occasions) are the people waiting for the current round. Scheduling a round creates an **event** (`app.events`, one per round) with one or more **groups** (`app.event_groups`), each inviting people (`app.group_members`: invited → confirmed/declined, confirmed → dropped). Invited people leave the signups; the rest roll over to the next round. A person is in at most one group per event (enforced by the database). Each plan names its venues when it opens (migration 00009: `venue_place_id`, `follow_up_venue_place_id`; approved venues first, never rejected ones, otherwise random so one café isn't in every plan); the groups of an event share them, and `event_groups.venue_place_id` is only for a group sent elsewhere. Only Google place ids are stored. Plans close as `done`, `no_group` or `withdrawn`.

**The worker** (`make worker`) runs a pass per city every hour (`plans.Runner`, timing in `plans.Timing`):

- **Travel-time refresh** (`refresh_maps`, daily, also on start): `geo.Refresh` rebuilds a city's matrix once it's 25 days old (`geo.RefreshAge`), replacing it whole so nothing outlives the 30-day Maps caching limit; without a Maps key it deletes rows past 30 days instead.
- **Meeting places** (`Runner.RefreshMeetingPlaces`, in each city pass before routes): for plans whose first activity has no venue (a photo walk), one Places Nearby Search near the area's centre, a station within 1 km and otherwise a park within 1.5 km, once per plan. Only the place id is stored (`plans.meeting_place_id`, migration 00013); the plan's steps then start with a "Meet here" stop whose name and address are fetched live, and its route starts there. Nothing happens without a Maps key.
- **Walks** (`Runner.Suggest` with a `walks.Composer`): a suggestion for a walking activity (one with a `walk_theme`) is composed before it opens, up to 4 per pass at once; the plan stores its title and summary (English, translated on demand), its stops in `app.plan_stops` (place id, role, minutes, note, walk from the previous stop) and its route. A walk that can't be composed isn't opened: matching is asked again for the next best plan, and the area and activity rest for 7 days (`app.walk_failures`). Model or Maps errors don't rest. Composed walks never get the old kind of meeting place; at scheduling every stop must be open from arrival to departure. The city pass may take up to 20 minutes (`MatchCityTimeout`).
- **Walk benchmark** (`tool walk-bench`, no database): compares proposers before changing the production model or prompt. `run -dry-run` lists the walks and estimated cost first; then `run` (resumable; `-sample 12 -reps 1` for a pilot, `-cases`, `-variants`, `-prompt file`, `-activities file` to try other themes), `judge`, `review` (writes `review.html` to fill in: each plan links to its walking route through every stop in Google Maps, and embeds it when `GOOGLE_MAPS_EMBED_API_KEY` names a key with the Maps Embed API; re-running keeps the pairs so answers stay valid; then `report -human review_answers.json`), `report` (writes `report.md`). Needs `GOOGLE_MAPS_API_KEY` and `GOOGLE_GEMINI_API_KEY`. Claude runs by default through the Claude Code CLI on your Claude subscription (`claudecode:` variants: sign in with `claude` once; each call runs in an empty directory with tools, settings and MCP off, never with an API key); `claude:` variants and judges use the API and need `ANTHROPIC_API_KEY`. Confirm a CLI winner on the API before switching production. Keep run directories out of the repo (they're large); commit only conclusions to the roadmap.
- **Plan routes** (`Runner.RefreshRoutes`, in each city pass after Suggest): the walk between a plan's two venues (or its meeting place and the follow-up's venue) from the Routes API, stored on the plan (encoded polyline and seconds) for its map and the timeline's walking time; computed when a plan opens, recomputed at 25 days, cleared at 30 (Maps caching terms), only for plans still open or with an event to come.
- **Opening hours** (in **Schedule**, below): before a round is saved, the plan's venues are checked (Place Details hours, once per venue per pass): the activity's venue must be open at the start and 90 minutes in, a follow-up's 2–3 hours after the start (activities have no stored duration). A closed time is taken out of the window and the engine schedules again; a venue closed for good (or until further notice) withdraws the plan, and a permanently closed one is marked `rejected` so it's never picked again. Lookup failures don't block scheduling.
- **Push notifications** (`plans.Notifier`, a `send_notifications` job every minute): the changes that notify people write rows to `app.notifications` in the same transaction (an outbox: invited when a round is scheduled; group confirmed, at quorum or at the deadline; group cancelled; a plan closed without a group, to whoever was still waiting, with `planId` instead of `eventId` so the app opens the feed; "How was it?"; crew offered, formed and plan suggested, with `crewId`, titled with the crew's name), and the job sends them through Expo (`internal/push`) to every device the person registered: the plan's title, then a line from the UI catalogue in their language (`push.*` keys; no dates, which Go can't format per language). Tokens Expo reports as `DeviceNotRegistered` are deleted; if Expo can't be reached, the batch is retried on later passes (5 attempts). The same job then checks **receipts** for pushes sent at least 15 minutes ago (`app.push_tickets`, kept a day): `DeviceNotRegistered` there deletes the token too, other refusals are logged.

0. **Settle** (which also deletes group chats 30 days after their event) groups whose confirmation deadline has passed: confirmed with at least `min_attendance`, otherwise cancelled; the people who had confirmed a cancelled group go back on the plan's waiting list (if it's still open), and an event with no group left is cancelled. Events whose date has passed are marked `done`. Once feedback opens (3 h after the start), everyone who went ahead with a group is sent "How was it?" (`event_feedback`), once per event.
0b. **Crews** (`crews.Runner.Pass`, after routes; failures are logged, not fatal): decide offers that everyone answered or that ran out; post a plan suggestion to active crews due one (a day after forming, then weekly); then offer new crews from `matching.FindCrews` over the city's met pairs, mutual picks, blocks and crew aversions, skipping sets offered before and crews overlapping an existing one on the same basis.
1. **Schedule** every open plan, most signups first (each event blocks its occasion for the people invited). Occasions start 2 days from today (time to confirm). Ready plans get an event; at the signup deadline (7 days into the 14-day window) the round goes ahead with whatever groups can form, or the plan closes as `no_group`. People not placed roll over to the next round, which starts in the same transaction; a plan with nobody left closes as `done`. A plan whose activity was disabled closes as `withdrawn`. Invitees answer by the start of the day before the event (local time). Events start at a set time for their part of the day (`Timing.BlockStarts`: 10:00, 14:00, 18:30 local), and their meeting point is shown to confirmed people from 24 hours before.
2. **Suggest** new plans up to the city's cap, with the activities in season in the month the round starts. Plans that closed as `no_group` in the last 14 days count as open, so they don't reopen the next hour.

Not done yet: chat, push notifications, the travel-matrix refresh and AI-written plan text.

## Matching

`internal/matching` runs **plan first, time second**: suggest plans without a date, rank them for each person, then schedule a plan once its signups can make a good group. The caller (the M6 worker and API) loads everything (users, approved venues, activities enabled and in season, the fastest travel time per area pair, open plans and signups, mutual picks and blocks) and stores the results; the engine itself does no I/O. **Relations** (M7): `MutualLinks` links two people who picked each other after outings, with the lower of their two pick return rates ((returned + 2) / (made + 2)), so someone who picks everyone counts for less; a report or a "rather not" blocks the pair for good. `FindCrews` finds crews in the graph of people who've met (maximal cliques, Bron–Kerbosch), keeping members with a mutual pick inside and a shared liked activity or home area.

1. **`Pools`:** every area is a candidate meeting place. A person joins each area they can reach within `max_travel_min`, in each language they speak fluently. Two-language pools exist only for the city's `language_pairs`, and anyone fluent in either language joins.
2. **`Suggest`:** for each pool, activities with a venue in the area (or needing only a meeting point) and an audience of at least `min_audience` people who want them and are usually free at a part of the day they suit (`activities.blocks`). Ranked by demand (love 2, like 1, open to try 0.5; × 0.3 if over budget) × venue choice, then taken best first across the city: not already open, at most `plans_per_pool` per pool, the same activity in a shared language at least `plan_spacing_min` minutes apart, at most one open plan per `users_per_plan` people. A non-conversational activity gets a food follow-up.
3. **`Feed`:** every open plan for one person, in levels (top = love, good = like, maybe = open to try, low = no preference or too far, not-for-you = doesn't speak its language) for the feed's order and the map's colours. Within a level: interest, momentum (signups so far), fit with their usual availability, then distance. A plan people they get on with (mutual picks) signed up for moves up a level and gains `weights.friends`; `ListFeed` returns the count as `friendsInterested`, never who.
4. **Signups:** `Signup.Pattern` is the weekly slots that suit them for this plan (nil = profile availability) and `Unavailable` the dates or occasions they can't do. The caller adds the occasions of events they're already going to.
5. **`Schedule`:** for each occasion in the plan's window, form groups from the signups free then (greedy, then local search: fill, replace, swap, spread small groups); keep the best occasion, ties to the earliest. Ready when a group reaches its target size; groups below the preferred size wait for the next round. With `force` (the signup deadline) every group that can form goes ahead. Each group invites its target plus `extra_invites`; `Quorum` confirms straight away and `MinAttendance` (2) is the fewest it can go ahead with at the confirmation deadline.

Hard rules (`Violation`): no blocked pairs; same-gender-only is respected; at least 2 people (`min_group_size`). There's no cap on friends: the score's friendship part (`friendship`) rewards clusters of people who picked each other. Removing people never breaks them, so they still hold after declines.

Preferences (in the group score, so the engine avoids them when it can but would rather go ahead than leave someone out): groups of at least 3 or the activity's own minimum (`preferred_min_size`, weight `min_size`); nobody the only woman or only man (weight `balance`; nonbinary and unspecified exempt). The only language rule is the event's: everyone speaks its primary or secondary language.

Settings are in `matching.Config` (`DefaultConfig`). A city overrides any of them with JSON in `app.cities.matching_weights`, e.g. `{"language_pairs": [["ja", "en"]], "users_per_plan": 15, "weights": {"mutual": 2}}`. Unknown keys are rejected.

```sh
make sim                                           # 500 synthetic users per city pack
make sim ARGS="-users 1000 -seed 2 -config '{\"language_pairs\":[[\"ja\",\"en\"]]}'"
```

The simulator runs the whole flow on synthetic users: suggest, signups from each person's feed (with varied availability), then scheduling (ready plans first, then the rest at their deadline), never double-booking anyone. It reports plans, signups, scheduling, group sizes, pairs, gender balance, who got invited by gender and language, and any rule violations, which fail the run. `go test ./internal/matching/sim` runs it for every pack in CI.

## Code generation

```sh
make gen   # from root: buf (Go + TS + docs), sqlc, and the UI-text copy (internal/uistrings/en.json)
```

The code generators are pinned as `tool` directives in `go.mod`, and `../go.work` makes `go tool` work from the repo root.
